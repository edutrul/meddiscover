# ADR 005: Solr lexical search and Reciprocal Rank Fusion

- Date: 2026-11-24
- Status: Implemented; pending review
- Approved scope: Phase 05, issue #10. No LLM generation, recommendation ranking, learned rankers, ANN indexes or external search providers.

## Context

Phase 03 ranks topics by meaning with local embeddings and pgvector. That approach handles paraphrases but has no notion of exact names, and it cannot explain matches in terms of the user's words. PLAN Phase 05 adds Apache Solr through DDEV for lexical retrieval, fuses both rankings with Reciprocal Rank Fusion (RRF), and requires an honest comparison. Hybrid search must not be assumed to be better.

## Decision

### Solr in DDEV

| Item | Choice |
|---|---|
| Add-on | `ddev/ddev-solr` **0.9.0**. Version 0.10.0 requires DDEV ≥ 1.25.5, and the project and CI use 1.25.2. |
| Image | `solr:9.11.0` (SolrCloud mode), pinned in `.ddev/docker-compose.solr-meddiscover.yaml` |
| Drupal | Search API 1.43 and Search API Solr 4.4 (Solr 9 support), with the `solr_cloud_basic_auth` connector |
| Server and index | `search_api.server.med_solr` and `search_api.index.med_topics`, exported in `config/sync` |
| Configset | Generated by Search API Solr from the exported configuration and uploaded with `drush solr-upload-conf med_solr --numShards=1`. The same module version and configuration produce the same configset, so it is not committed as a copy. |
| Credentials | Exported configuration stores none. `settings.php` injects the add-on's public local defaults only when `IS_DDEV_PROJECT` is set. |
| Isolation | `site_hash: true`, so a clean verification install sharing the DDEV collection only sees its own documents |

**Privacy:** by default, Solr logs every request at INFO level and Jetty writes a request log; both record query text. The compose override sets `SOLR_LOG_LEVEL=WARN` and `SOLR_REQUESTLOG_ENABLED=false`. The slow-query log is disabled (`slowQueryThresholdMillis` is unset, so it stays at -1). Backend exceptions are replaced with a generic message so request details never reach the Drupal log. This was verified after form submissions on all three routes.

### Index

The index holds the English, published Health Topics of the corpus that pgvector also covers.

| Search API field | Source | Type | Boost |
|---|---|---|---|
| `title_unstemmed` | Title | unstemmed full text | 21 |
| `title` | Title | English full text | 13 |
| `also_called_unstemmed` | Also called | unstemmed full text | 13 |
| `also_called` | Also called | English full text | 8 |
| `mesh` | MeSH descriptor labels | English full text | 5 |
| `see_reference` | See references (MedlinePlus redirects, often shared) | English full text | 3 |
| `description` | Meta description | English full text | 3 |
| `summary` | Plain-text summary | English full text | 1 |
| `groups` | MedlinePlus group names | English full text | 1 |
| `source_id`, `nid`, `status` | Canonical ID, node ID, published flag | string, integer, boolean | — |

- **Datasource and processors.** The datasource is limited to the `med_health_topic` bundle and English. The entity-status processor drops unpublished topics, and the HTML filter is applied.
- **Indexing.** Topics are indexed immediately on save, and changes to referenced MeSH and group terms are tracked.
- **English analysis.** `text_en`: standard tokenizer, English stopwords, word-delimiter splitting (verified with Solr's analysis API: `HbA1c` → `hba1c`, `hba`, `a1c`, so it matches the A1C topic), lowercasing and Snowball Porter stemming.
- **Unstemmed copies.** Titles and alternative terms are also indexed in unstemmed form, which rewards exact word forms over stem-only matches.
- **No synonyms file.** MedlinePlus alternative terms and see references already exist as indexed fields, so a hand-written list would duplicate and drift from the source data.

### Lexical query

`LexicalSearch` runs a Search API query with these settings:

- **Parser.** EDisMax, forced with `defType=edismax` over the index's boosted fields. Search API Solr's own “Multiple words with EDisMax” parse mode applied the field list only to the first word (`+id:disk` for “slipped disk”), so it is not used. Search API escapes the keys, so `*:*` or `title:` are searched as text.
- **Matching rule.** OR conjunction with minimum-should-match `mm=2<75%`. Queries of one or two words need every word; longer queries need 75 % of them. Pure AND returned nothing for natural sentences, and pure OR matched most of the corpus on unrelated queries.
- **Phrase boosts.** `pf` adds phrase boosts on the unstemmed title (21), unstemmed alternative terms (13) and see references (5).
- **Exact names.** When the whole query equals a topic's title, alternative term or see reference (case- and punctuation-insensitive), that topic moves first. Solr order is kept within the promoted and remaining groups.
- **Ambiguity.** When an exact name belongs to several topics, all of them are returned and a notice names them. For example, “Sugar diabetes” refers to Diabetes and Diabetes Type 2. The system never picks one silently.
- **Score display.** Solr scores are shown with “comparable only within this search”, because they are not probabilities.

### Hybrid query (RRF)

`HybridSearch` asks each strategy for its **accepted** results, up to `hybrid_depth` (20) each: lexical results that pass minimum-should-match, and semantic results at or above the 0.62 cosine threshold. It then fuses them by canonical MedlinePlus topic ID:

```
RRF(d) = Σ over strategies 1 / (k + rank_s(d)),   k = 60, ranks start at 1
```

- **Ranks, not scores.** Solr scores (unbounded, query-dependent) and cosine similarities (bounded, model-dependent) are never added or normalized together.
- **Zero results stay possible.** Fusing only accepted results means an unrelated query can still return nothing; fusing the full semantic ranking would always return 24 topics.
- **Deduplication.** Fusion merges results by canonical ID, and a repeated ID inside one list keeps its first rank.
- **Ties.** Ties are broken by: appearing in more lists, then the better best rank, then the strategy order (lexical before semantic, because lexical acceptance requires the query's words), then the ID. The ordering is deterministic.
- **k = 60.** This is the value from Cormack, Clarke and Büttcher (2009), fixed before evaluation. With two short, overlapping lists, no k between 0 and 1000 changed any top-5 ranking in the evaluation ([results](../evaluation/hybrid-search.md#k-sensitivity)). k only matters when a document ranked high in one list competes with documents ranked lower in both.
- **Degradation.** If one retriever fails (Solr down or embedding provider unavailable), hybrid ranks with the other and shows a notice. If both fail, it reports the error. Invalid queries are never hidden by degradation.

### Shared architecture

- **Common contract.** `SearchStrategyInterface` defines `id()`, `search($query, $limit)` and `describeScore($result)`. All strategies return `results[]` with `node`, `id`, `score` and `ranks`, plus `timings` and `notices`. `SemanticStrategy` adapts the Phase 03 service without changing it.
- **One form, three routes.** `SearchForm` serves `/search/semantic`, `/search/lexical` and `/search/hybrid`. The route's `strategy` default selects the service. Rendering, the Phase 04 enrichment, links between search modes, error messages and the privacy handling (POST only, no form cache, temporary state) are shared.
- **Query rules.** `QueryText` holds the shared rules: 1–500 characters and a limit of 1–20.

## Evaluation summary

On 48 reviewed synthetic queries ([full results](../evaluation/hybrid-search.md)):

- **Hybrid.** It has the best recall (R@5 0.96, against 0.90 semantic and 0.79 lexical) and the best MRR (0.97). It never returned an empty result for a query with relevant topics.
- **Semantic.** It is the most reliable at rejecting unrelated queries (10 of 10 empty).
- **Lexical.** It matches semantic on exact names and alternative terms, but misses 45 % of paraphrases. It returned topics for one unrelated query, “How do I change a car tire?”, because the question words count toward minimum-should-match (see Limitations). Hybrid inherits that false positive.
- **Latency.** Hybrid costs about 3 ms more than semantic at the median (16.5 ms against 13.4 ms; lexical alone 2.3 ms).

## Alternatives considered

- **Score normalization.** Min-max or z-score normalization of Solr and cosine scores, followed by a weighted sum, was rejected. Normalization depends on each query's result set and needs tuned weights, and PLAN forbids unjustified score mixing.
- **Search API Database backend.** This would avoid running Solr, but PLAN requires Solr and the database backend has no BM25 field boosting or EDisMax.
- **Committing the generated configset.** It is reproducible from exported config, so a committed copy would only drift.
- **Fusing all semantic candidates.** This was rejected because it removes every zero-result answer.

## Limitations and follow-up

- **Question words in should-match.** The English stopword list has no question words (“how”, “do”, “I”, “my”, “why”), and unstemmed fields keep them. They count toward minimum-should-match and can match topic text: “How do I change a car tire?” returned diabetes topics, and “Information about seasonal allergies” returned nothing. Query-side stopword handling (or consistent stopwords across fields) is a Phase 08 optimization candidate. It was not tuned here, to keep the evaluation honest.
- **Settings chosen on development probes.** `mm` was chosen on development probes that overlap the evaluation queries, so the lexical results are optimistic rather than a held-out estimate. Field boosts are editorial, not tuned.
- **Lexical-first ties.** The lexical tie preference occasionally ranks a weak lexical match above a strong semantic one. For example, “How do I pick a good doctor?” ranks How to Prevent Diabetes above Choosing a Doctor.
- **Corpus size.** With 24 topics the metrics are coarse; one query moves a category's rate by 7–20 points.
- **Clean environments need the configset upload.** Solr must be running with the uploaded configset. A clean environment needs `solr-upload-conf` once before indexing, as CI does.
